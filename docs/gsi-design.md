# GSI 实时教练 — 产品设计（v0.1 草案）

> 状态：设计阶段，未动工。定位为我们"赛后复盘"产品线的姊妹篇：**赛中实时教练**。
> 两者构成完整闭环：赛中提醒（GSI）→ 赛后复盘（get_match_coaching）。

## 1. 背景与机会

- 全网 Dota MCP 摸底（2026-09）结论：历史数据赛道我们已无对手；实时维度只有
  ismaelMoreau/Dota_2_MCP_Server_ 一个 2★ 早期项目（GSI→Discord 符文播报）。
- Valve 官方提供 **Game State Integration (GSI)**：游戏客户端主动把对局状态 POST
  到本地 HTTP 端点。官方支持、只读、无需注入——无反作弊风险。
- 机会：把 GSI 状态流变成 agent 可查询的结构化数据 + 派生教练结论（计时器、
  经济、冷却），"打游戏时问一句现在该干嘛"。

## 2. GSI 机制速览

- 配置：`game/dota/cfg/gamestateintegration/*.cfg` 声明推送目标（URL）、频率、
  关注的数据块。游戏运行时按事件（符文/击杀/买活…）和间隔（默认 ~1s 可调）推送。
- 载荷：嵌套 JSON——`map`（时间/比分/白天黑夜）、`player_N`（每个玩家：英雄、
  等级、击杀、金钱、买活金、物品栏+库存+冷却、技能等级+冷却、死亡状态）、
  `events`（事件流）、`minimap`（可见单位坐标）、`roster`、`courier` 等。
- 关键限制：**只有本队完整数据 + 敌方可见信息**（克制视角，天然公平）。
- 推送目标是本机/局域网 HTTP——架构必须围绕"接收器离游戏近、agent 可能远"。

## 3. 架构选项（三选一，推荐 A→C 渐进）

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| **A. 集成本 MCP（MVP 推荐）** | 本 MCP 增加可选 GSI 模式：`OPENDOTA_GSI_PORT=4000` 启动接收端点 + 新工具 `get_live_game_state` | 零新仓库；复用 MCP/缓存/多语言；游戏机上 `npx opendota-mcp` 即用 | 跨机器（Mac 容器里的 agent）要二期 |
| B. 独立接收服务 | 单独常驻小服务收 GSI，本 MCP 加工具查询它 | 多消费者、游戏机零依赖我们的包 | 两个进程两份配置，起步重 |
| C. 推送同步 | 接收器把快照推到公网服务器，任何 agent 查 `get_live_game_state` | agent 与游戏机解耦，openclaw/朋友都能看 | 需鉴权与节流；公网依赖 |

**推荐路径**：A 做通数据链路与教练逻辑 → C 解决"agent 在另一台机器"（我们的
实际拓扑：Windows 打游戏 / Mac 容器跑 openclaw）。B 不做。

## 4. MVP 范围（方案 A）

**输入**：一条 `install-gsi` 命令生成 cfg（写入 Steam 目录或打印让用户放置）。

**核心工具 `get_live_game_state`**（GSI 未连接时返回引导信息）：
- `map`：游戏时间、比分、昼夜、剩余比赛时长预估
- `me`：英雄/等级/金钱/买活金/ respawn 倒计时、技能冷却表、物品冷却表
- `team`：队友状态同上（谁有大招、谁死了多久复活）
- **派生教练层**（服务端算好，明文中文，复用我们的数据哲学）：
  - 符文计时：神符/赏金符下次刷新倒计时（含前 2 秒预警文案）
  - Roshan：击杀时间→重生窗口（8-11 分钟机制，Aegis 掉落提醒）
  - 买活建议：死亡时"买活花 X 金，买后剩 Y，建议存/买"
  - 大招就绪表：全队 ult 状态（"斯温大招还有 34s"）
  - 物品提醒：魔瓶充能、TP 冷却、关键装（BKB）冷却
  - 事件流摘要：最近 60s 的击杀/塔/符文事件
- 与历史数据联动：`get_live_game_state` 的英雄名/物品名直接复用 28 语言表；
  敌我阵容可实时调 STRATZ 克制查询（"对面这个阵容我该出什么"比赛中也能答）

**不做（一期）**：主动推送、敌方数据推测、小地图图像分析。

## 5. 二期：主动教练 + 跨机器

- **触发器**：接收器内置规则引擎（符文<10s、Roshan 窗口开启、队友买活金够）
  → Webhook/openclaw 消息/Discord 频道（可 TTS，参考 ismaelMoreau 但做成可选）
- **跨机器（方案 C）**：快照节流（≥2s）推送到自托管公网实例的 `/gsi-ingest`
  端点（复用现有 Bearer 门禁），openclaw 那侧的 MCP 通过 `get_live_game_state`
  读最近快照——同一工具名，两种数据来源，agent 无感。
- 隐私：快照仅在本机/自己的服务器间流动，不进第三方。

## 6. 风险与开放问题

1. **cfg 安装体验**：Steam 路径自动探测（注册表/常见路径）vs 打印让用户手放？
2. **推送频率与状态体积**：全量块 1s 一次约 50-200KB；按块订阅（只订 map+me+team）控制。
3. **时钟基准**：GSI 的 `map.clock_time` 与现实时间对齐（暂停处理）。
4. **多局并发/重连**：状态机按 match_id 重置。
5. **Windows-first**：用户主要在 Windows 打游戏（含本机），接收器需后台常驻方式
  （计划任务/nssm？或复用 ZCode 本地会话存活期）。
6. 英雄/物品新增时 GSI 字段的兼容性（内部名驱动，同别名表策略）。

## 7. 与现有资产的关系

- 复用：多语言表（英雄/物品/技能名）、别名表、fuzzy、数据哲学（明文+证据）、
  HTTP 部署与门禁、SKILL/instructions 引导层。
- 新增：GSI 接收器（~150 行）、状态机与派生计算层、`get_live_game_state` 工具、
  install-gsi 命令、（二期）推送与触发器。
- 品牌延续：赛后有 `get_match_coaching`，赛中就叫 **live coaching**。

## 8. 建议里程碑

- M1（1 个工作日量级）：方案 A 全链路——cfg 生成、接收器、快照状态机、
  get_live_game_state（含符文/Roshan/买活三个最值钱的派生）、本地真机联调。
- M2：大招/物品/事件层、SKILL 与 instructions 更新、多语言。
- M3（二期）：方案 C 跨机器 + 主动触发器 + openclaw 实战验证。
